## Summary

Give every tenant a starting library of managed coaching videos (one per canonical behaviour), so a programme's bundle can be built on day one without every customer uploading URLs. Managed items are ordinary `elevate_learning_items` rows with `source = 'managed'` and a stable `managed_key`. The catalogue is a Python constant shipped with the code; a **job** upserts it into a tenant schema — at onboarding (docs/03 §1 step 7) and again whenever the catalogue changes. **No data migration**: a schema migration runs once per schema and can never "re-migrate" an edited list into tenants that already applied it, and product content is not schema.

## Background

### What exists today (current architecture)

- `elevate_learning_items` (FOUNDATION-3): `title`, `url` (https), `category` (canonical `event_type`), `source ∈ {managed, customer_url}`, **`managed_key text NULL`** with `uq_elevate_learning_items_managed_key` (unique, `WHERE managed_key IS NOT NULL`) — both created by revision `0003`.
- Registry/mapping data ships as Alembic data migrations (`docs/01` §6) — that is **platform configuration**, identical for every tenant and changed only by a deploy. The managed video list is per-tenant product content that an admin may extend or replace — the analogue is the provisioner seeding default `tenant_streams` at onboarding, not a registry migration.
- Elevate jobs follow the index "Job conventions": Cloud Run job, `uv run python -m app.elevate.jobs.<name> [--tenant T]`, structured report.
- 14 canonical behaviours in `docs/08` §1.

### What this story does (the proposed change)

1. `backend/app/elevate/learning/managed_catalogue.py`: `MANAGED_VIDEOS: list[ManagedVideo]` — `ManagedVideo(key, title, url, category)` validated at import (`shapes.py` strict model; keys unique, `url` https, `category ∈ docs/08 §1 or None`). May be empty.
2. `backend/app/elevate/jobs/seed_managed_library.py`: per entitled tenant (or `--tenant`), one transaction: upsert every catalogue entry by `managed_key` (`INSERT … ON CONFLICT (managed_key) WHERE managed_key IS NOT NULL DO UPDATE SET title, url, category, updated_at = now()`); report `rows_inserted`, `rows_updated`, `rows_unchanged` per tenant. Never deletes — a key removed from the catalogue leaves the tenant's row in place (a programme may reference it); removal is an admin action.
3. `backend/app/elevate/learning/service.py::import_managed(conn, items, actor) -> ImportResult`: the service behind the admin import — validates `[{title, url, category}]` (≤ 200), inserts `source = managed`, `managed_key = NULL`, skips URL duplicates, writes `elevate_config_audit` rows in the same transaction (ELEV-004 pattern). **The route** `POST /v1/elevate/learning-items/import` is delivered by API-2 at build step 21 (D16: no route before the UI pass); this story ships the service and its tests only.
4. docs/03 §1 step 7 (FOUNDATION-8 wording) gains: run `seed_managed_library --tenant <T>` before creating the first programme.

### Why we're making this change (per the decision log)

Contract §05: *"Learning videos may use the same behavior-category metadata as source rules so the builder can find relevant content"*; a builder with an empty library cannot show "videos for speeding". §12 M2: seeding by migration was rejected because (a) a revision runs once per schema — editing the catalogue and "re-migrating" cannot update tenants that already applied it (Codex finding); (b) importing a mutable constant into a revision breaks the frozen-DDL rule; (c) it forced revision `0009` at build step 03b, before `0004`–`0008` exist.
