## Summary

The three read queries both scoring jobs share, as functions taking an `AsyncConnection` already pinned to the tenant schema: who drove and how far (`trips`), how many distinct incidents per driver per `dedup_group` under a rule set (the view, with an argmax over weight), and how many incidents were excluded for attribution. All windows are half-open UTC instants.

## Background

### What exists today (current architecture)

- `trips` (`backend/app/db/models/tenant.py:297–320`): `driver_id` (`:305`, nullable), `started_at` (`:308`), `distance_m` (`:310`, nullable int). Index `ix_trips_driver_started (driver_id, started_at)` (`:317`).
- `elevate_scoring_events` view (FOUNDATION-4): `incident_id, driver_id, incident_driver_id, driver_attribution, occurred_at, vendor_id, vendor_event_ref, category`.
- `trips.driver_id` is explicit-only today (`backend/app/processing/enrichment.py:17`) — P#1.
- Tenant access: `tenant_connection(tenant_id)` yields an `AsyncConnection` inside one transaction with `SET LOCAL search_path` (`backend/app/db/session.py:44–56`).

### What this story does (the proposed change)

Creates `backend/app/elevate/queries.py` with three async functions built with SQLAlchemy Core against `app.db.models.tenant.trips` and `app.elevate.models.elevate_scoring_events`. No writes.

### Why we're making this change (per the decision log)

- R1/D8: *"population comes from exposure"* — a driver with miles and no incidents must score 100.
- R11: charge on `elevate_scoring_events.driver_id` (the report's own driver), never `incident_driver_id`.
- D7: count only `driver_attribution IN ('explicit','inferred')`; count the rest for display.
- D13: one count per (incident, group) under the highest-weighted matched rule → `DISTINCT ON (incident_id, dedup_group) … ORDER BY weight DESC`.

async def rule_counts(
    conn, *, since: datetime, until: datetime,
    rules: list[tuple[str, str, str, Decimal]],   # (vendor_id, vendor_event_ref, dedup_group, weight)

    # (driver_id, "vendor_id:vendor_event_ref") -> COUNT(DISTINCT incident_id) for the highest-weighted matched rule

> **D17 — one scoring component, two callers.** `score_window()` is the only function that turns a window into scores. A static test (`test_score_window_is_sole_caller`) greps `backend/app/elevate/jobs/` for `programme_score(` and fails on any hit — the jobs may only call `score_window`.

```sql
-- SQL-1 population (trips)
SELECT driver_id, SUM(distance_m)::numeric / 1609.344 AS miles
FROM trips
WHERE driver_id IS NOT NULL AND distance_m IS NOT NULL
  AND started_at >= :since AND started_at < :until
GROUP BY driver_id;

-- SQL-2 group counts (view join VALUES), argmax over weight per (incident, group)
WITH rules(vendor_id, vendor_event_ref, dedup_group, weight) AS (VALUES (:v1,:r1,:g1,:w1), ...),
hits AS (
  SELECT DISTINCT ON (v.incident_id, r.dedup_group)
         v.incident_id, v.driver_id, r.dedup_group, r.vendor_id, r.vendor_event_ref
  FROM elevate_scoring_events v
  JOIN rules r ON r.vendor_id = v.vendor_id AND r.vendor_event_ref = v.vendor_event_ref
  WHERE v.occurred_at >= :since AND v.occurred_at < :until
    AND v.driver_id IS NOT NULL
    AND v.driver_attribution IN ('explicit','inferred')
    AND v.incident_driver_attribution <> 'contradiction'
  ORDER BY v.incident_id, r.dedup_group, r.weight DESC, r.vendor_id, r.vendor_event_ref
)
SELECT driver_id, vendor_id || ':' || vendor_event_ref AS rule_key, COUNT(DISTINCT incident_id) AS n
FROM hits GROUP BY driver_id, vendor_id, vendor_event_ref;

-- SQL-3 excluded (display only, D7)
WITH rules(...) AS (VALUES ...)
SELECT COALESCE(v.driver_id, v.incident_driver_id) AS driver_id, COUNT(DISTINCT v.incident_id)
FROM elevate_scoring_events v JOIN rules r ON (r.vendor_id, r.vendor_event_ref) = (v.vendor_id, v.vendor_event_ref)
WHERE v.occurred_at >= :since AND v.occurred_at < :until
  AND (v.driver_attribution NOT IN ('explicit','inferred') OR v.driver_id IS NULL
       OR v.incident_driver_attribution = 'contradiction')
GROUP BY 1 HAVING COALESCE(v.driver_id, v.incident_driver_id) IS NOT NULL;
```

Build the `VALUES` list with `sqlalchemy.values(...).data([...])` (SQLAlchemy 2.0); never string-format rule names into SQL.

## Assumptions

1. `distance_m` is metres — *Source: column name `tenant.py:310`; `normalizer.py:281–285` converts km→m on ingest.*
2. `occurred_at` on the view is the event's own timestamp (vendor clock) and is the correct bucketing clock — *Source: D8.*
3. `DISTINCT ON … ORDER BY … weight DESC, vendor_id, vendor_event_ref` yields a deterministic argmax — *Source: PostgreSQL `DISTINCT ON` semantics.*

## Reliability

Empty rule list: SQL-2 must short-circuit and return `{}` (a `VALUES` with zero rows is invalid SQL) — guard in code.
